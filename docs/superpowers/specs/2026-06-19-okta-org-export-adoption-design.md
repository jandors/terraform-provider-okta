# okta-org-export — Brownfield Org Adoption Process — Design

**Date:** 2026-06-19
**Status:** Approved (design phase)
**Related:** [2026-06-15-okta-multi-stage-management-design.md](2026-06-15-okta-multi-stage-management-design.md), [2026-06-18-okta-dev-local-environment-design.md](2026-06-18-okta-dev-local-environment-design.md)

## Goal

A reusable, scriptable process — in a new repo **`okta-org-export`** — that
reverse-engineers an existing ("brownfield") Okta org into Terraform-managed
configuration (HCL **and** state), then layers our test configuration on top,
**without deleting any existing org config**.

First test case: the trial org `trial-5536990.okta.com`.

## Decisions (locked)

| Area | Decision |
|---|---|
| Output | **Adopt into Terraform** — generate HCL *and* import into state, so TF manages existing resources going forward. |
| Scope | **Everything in the org**, achieved via an extensible resource-type registry; system-managed defaults are **curated out**. |
| Nature | **Reusable process** (scripts + runbook), parameterized per org. Trial org is the first test case. |
| Mechanism | **Native** Terraform `import` blocks + `terraform plan -generate-config-out` (no third-party exporter). |
| Placement | **New dedicated repo** `okta-org-export`; per-org generated output lives under `workspaces/<org>/`. |
| Discovery auth | Read-only **SSWS token** (`OKTA_EXPORT_TOKEN`) for the script; Terraform import/apply uses the org's normal auth (OAuth2 here). |
| Safety | Generate-before-import; add-only config; a hard "0 to destroy" gate before any apply. |

## Why Terraform can't delete existing config

Terraform only acts on resources in its configuration + state. It never touches
unmanaged resources. The only deletion risk is importing a resource and later
removing it from config — which this process structurally prevents (see
[Safety model](#safety-model)).

## Repository layout

```
okta-org-export/
├── README.md                 # what it is + safety model
├── runbook.md                # the 7-stage process (primary deliverable)
├── discover.py               # Okta API → import blocks (stdlib only)
├── resource-types.json       # registry: API endpoint → TF type → id/name fields
├── skip-list.json            # system/default resources to exclude (curation)
├── templates/
│   ├── provider.tf           # okta provider + local backend seed for a workspace
│   └── versions.tf           # required_version + required_providers
├── .gitignore                # workspaces/*/, *.tfstate*, .terraform/, *.pem, tokens
└── workspaces/
    └── <org>/                # per-org output (gitignored by default — see PII note)
        ├── imports.tf        # generated by discover.py
        ├── generated.tf      # generated by terraform -generate-config-out
        ├── test-config.tf    # our added test configuration
        ├── skip-extra.json   # optional per-org extra exclusions
        ├── provider.tf       # from templates/
        ├── versions.tf       # from templates/
        ├── manifest.json     # audit log: discovered / kept / skipped (+reason)
        └── terraform.tfstate # local (gitignored)
```

This repo is a sibling of `okta-base-config`, `okta-dev-local`, and the env
repos under the workspace root. Whole-org generated HCL stays here and never
pollutes the curated `okta-base-config` modules.

## The adoption pipeline (7 stages)

```
1. DISCOVER   discover.py lists every resource ID per registered type via the
              Okta API, skipping anything matched by skip-list → writes imports.tf
2. GENERATE   terraform plan -generate-config-out=generated.tf
              → TF writes HCL for every import target using the real okta schema
3. CURATE     review generated.tf; fix the known gaps; confirm skip-list caught
              the system defaults
4. IMPORT     terraform apply  → import blocks pull existing resources INTO state
              (creates nothing, deletes nothing)
5. VERIFY     terraform plan  → MUST read "0 to add, 0 to change, 0 to destroy"
              (proves generated HCL matches the live org). Non-zero destroy = STOP.
6. ADD TEST   add test-config.tf (our tf-sandbox group) → plan shows ONLY +1 add
7. APPLY      terraform apply → existing config untouched, test config created
```

Requires Terraform >= 1.5 (`-generate-config-out`); we run 1.15 locally / 1.9.8 in CI.

## `discover.py`

A single Python script, **standard library only** (`urllib`, `json`; YAML via a
tiny bundled parser or accept JSON registry files to avoid a PyYAML dependency —
see Implementation note).

Inputs (env vars):
- `OKTA_ORG_NAME` — org subdomain (e.g. `trial-5536990`)
- `OKTA_BASE_URL` — `okta.com` / `oktapreview.com`
- `OKTA_EXPORT_TOKEN` — read-only SSWS API token (discovery is read-only and
  ephemeral; one `Authorization: SSWS <token>` header, no JWT signing in-script)

Behavior:
1. Load `resource-types.json` + `skip-list.json` (+ optional per-org `skip-extra.json`).
2. For each registered type: GET the list endpoint; follow the `Link: rel="next"`
   pagination header until exhausted.
3. For each item: apply curation (below). If kept, derive a deterministic, valid
   HCL identifier from the name/id (lowercase; non-alphanumerics → `_`; prefix if
   it starts with a digit; de-duplicate collisions with a numeric suffix) and emit:
   ```hcl
   import {
     to = okta_group.grp_engineering
     id = "00g1abc2d3EXAMPLE"
   }
   ```
4. Write `workspaces/<org>/imports.tf` and `workspaces/<org>/manifest.json`
   (every item: kept or skipped, with the skip reason).

**Implementation note:** registry/skip files are **JSON**, not YAML, so the
script parses them with the stdlib `json` module and needs no PyYAML
dependency — keeping the "stdlib only" constraint true.

## Resource-type registry

Each entry maps an API endpoint to a Terraform resource type. "Everything in the
org" = growing this registry; the script is generic over it. The registry lists
**only importable types**; types the okta provider can't import are omitted and
that gap is logged.

Starter entries (extend over time):
```json
[
  { "tf_type": "okta_group",        "api": "/api/v1/groups", "id_field": "id", "name_field": "profile.name" },
  { "tf_type": "okta_user",         "api": "/api/v1/users",  "id_field": "id", "name_field": "profile.login" },
  { "tf_type": "okta_network_zone", "api": "/api/v1/zones",  "id_field": "id", "name_field": "name" }
]
```

Two types need discriminators:
- **Apps** (`/api/v1/apps`) return all app types in one list; each maps to a
  different TF resource (`okta_app_oauth`, `okta_app_saml`, …) keyed off
  `signOnMode`. The entry carries a `type_map`.
- **Policies** (`/api/v1/policies?type=...`) must be queried per policy `type`
  (`OKTA_SIGN_ON`, `PASSWORD`, `MFA_ENROLL`, …), each → its TF resource.

## Curation

### Skip-list (applied during discovery, before emitting import blocks)

A resource is dropped if **any** rule matches:
```json
{
  "auto_skip_when": [ { "system": true }, { "default": true } ],
  "okta_group":       { "names": ["Everyone"] },
  "okta_app":         { "names": ["Okta Admin Console", "Okta Dashboard", "Okta Browser Plugin"] },
  "okta_auth_server": { "names": ["default"] }
}
```
`auto_skip_when` checks the API object's own attributes (built-in groups,
default policies, the default auth server). This keeps a trial org's pile of
Okta-managed defaults out of the import set so Stage 5 can reach "0 changes".

### `generated.tf` fix-ups (Stage 3)

`-generate-config-out` is best-effort; the runbook enumerates the known gaps so
curation is concrete, not vague:
- **Write-only/secret attributes** (client secrets, `password`) come back
  empty/null → remove them; they aren't readable.
- **Cross-resource references** are emitted as literal IDs (not interpolations) —
  fine for a snapshot/adoption; left as-is.
- **Occasional malformed nested blocks** → hand-fix until `terraform validate` passes.
- Any resource that can't be made plan-clean → move to the skip-list and re-run.
  Never force it.

## Adding the test configuration (Stage 6)

`test-config.tf` manages `tf-sandbox-engineering` via the same `groups` module as
`okta-dev-local`:
```hcl
module "test_groups" {
  source = "../../../okta-base-config/modules/groups"
  groups = {
    "tf-sandbox-engineering" = { description = "Local sandbox group (Terraform test)" }
  }
}
```

**Collision handling:** the test group is added to the **skip-list** so discovery
never imports it; it is managed **solely** by `test-config.tf`. If it already
exists in the org (from the earlier `okta-dev-local` test), a one-line `import`
block maps it to the module address
`module.test_groups.okta_group.this["tf-sandbox-engineering"]` — adopted, not
duplicated, never destroyed.

## Cross-org reuse

Parameterized entirely by env vars + the shared `resource-types.json` /
`skip-list.json`. Adopting another org = set the env vars, create
`workspaces/<that-org>/`, re-run `discover.py`, follow the same 7 stages. Per-org
extra exclusions go in `workspaces/<org>/skip-extra.json`.

## Safety model

1. Config is **generated from what exists** before any import.
2. The process only ever **adds** config — never removes a resource block.
3. **Stage 5 is a hard gate:** `terraform plan` must read `0 to destroy`; any
   other value means stop and curate/skip — never apply.
4. System defaults are **curated out**, so the process never tries to manage (or
   risk breaking) Okta-owned resources.
5. The test group is **skip + explicitly-managed**, so adoption and test config
   never fight over it.

## Privacy (PII)

Generated `okta_user` HCL and `manifest.json` contain PII (logins, emails,
profile fields). Default: **`workspaces/*/` is gitignored**. Committing a per-org
snapshot is opt-in and only for orgs confirmed safe (e.g. this trial org). Prefer
excluding `okta_user` from anything committed.

## Success criteria (trial org)

- `discover.py` produces `imports.tf` with the curated resource set and a
  `manifest.json` showing what was skipped and why.
- After Stage 4 import, **Stage 5 `terraform plan` shows `0 to add, 0 to change,
  0 to destroy`**.
- After Stage 6, `terraform plan` shows exactly **`1 to add`** (the test group).
- No existing org resource is modified or destroyed at any stage.

## Out of scope

- A third-party exporter (terraformer) — using native import + generate-config.
- Managing Okta system/default resources.
- Folding adopted resources into the curated `okta-base-config` modules (the
  adoption workspace is intentionally separate, flat generated HCL).
- Wiring adopted orgs into the DEV/TEST/PROD promotion pipeline.
- Remote state for adoption workspaces (local state; this is a snapshot/adoption tool).
